# Migrations

How the database schema changes, and the rules that keep a change from becoming an incident.

Everything here was settled while building M1 (PD-22 … PD-26) and is enforced by CI where it can be.

---

## The one rule

**The application never migrates.** `prisma migrate dev` is a local command; `prisma migrate deploy` is a release step run before the new image serves traffic. Nothing in `apps/api/src` calls either — the boot path connects and nothing more.

That is not merely tidy. An application that migrates on boot turns a rolling deploy into a race between replicas, and a crash-loop into a schema mangled by half-applied changes.

## Everyday flow

```bash
cd apps/api                         # prisma.config.ts lives here
pnpm exec prisma migrate dev --name what_changed
```

`prisma.config.ts` loads the repository-root `.env`, so no extra environment setup is needed. Prisma 7 removed `url` from the datasource block and stopped loading `.env` on its own; without that file, `prisma migrate` fails with _"datasource.url property is required"_.

**Naming:** `snake_case`, describing the change rather than the ticket — `init_identity`, `catalog_mirror`, `economy_check_constraints`. Prisma prefixes the timestamp. A reader scanning the folder should see what the schema became, not which ticket was open at the time.

Commit the generated folder with the code change that needs it. A migration merged without its schema, or a schema merged without its migration, fails CI.

## Rolling a change back

Prisma has no down migrations, and that is deliberate — a reverse script written in advance is rarely the one you need in the moment.

**Not deployed yet, local only.** Delete the migration folder and rebuild the database from history:

```bash
docker compose down -v && docker compose up -d --wait
cd apps/api && pnpm exec prisma migrate deploy
```

`prisma migrate reset` does the same in one step, but it is blocked for AI agents without explicit consent, and the sequence above destroys nothing that is not already reproducible.

**Already deployed.** Roll _forward_ with a migration that reverses the change. Prisma will write the SQL for you, using the previous schema as the target:

```bash
cd apps/api
git show HEAD~1:apps/api/prisma/schema.prisma > /tmp/previous.prisma
pnpm exec prisma migrate diff \
  --from-schema prisma/schema.prisma \
  --to-schema /tmp/previous.prisma \
  --script
```

Review the output before using it. `migrate diff` generates a `DROP` for anything the previous schema did not have, which is correct as a reversal and catastrophic if the column has since collected data.

## Changing a column safely

Never in one step. **Expand, backfill, contract**, as three separate deploys:

1. **Expand** — add the new column as nullable, or add the new table. Old code ignores it; new code writes both.
2. **Backfill** — populate it for existing rows. A migration for small tables, a job for large ones.
3. **Contract** — make it `NOT NULL`, drop the old column.

Between any two steps the running application may be either version, so each step has to work with both. Collapsing them is what turns a deploy into downtime.

## What CI enforces

The `migrations` job is the only one with a database — a `postgres:17-alpine` service of its own. It does two things that nothing else can:

| Check | Catches |
| --- | --- |
| `prisma migrate deploy` into an empty database | a migration that does not apply from scratch, including the hand-written ones |
| `prisma migrate diff --from-migrations --to-schema --exit-code` | a schema edited without a matching migration, or the reverse |

The diff needs a `shadowDatabaseUrl` — replaying a history to compare it has to replay it somewhere — which is why this job needs the service at all. Verified both ways: with the schema and history in agreement it reports _No difference detected_ and exits 0; with one field added to the schema and no migration it names the column and exits 2.

## Conventions

**Tables are `@@map`ped to plural snake_case**; Prisma models stay PascalCase. `user` and `set` are reserved words in PostgreSQL — unmapped, the tables would be `"User"` and `"Set"`, and `select * from user` in psql silently returns the current database user instead of failing.

**All enums live together** at the top of the schema, added ahead of the models that use them, so one migration creates every enum type.

**`@default(cuid())` is generated by the Prisma client, not by the database.** The column has no `DEFAULT` in PostgreSQL, so any raw `INSERT` must supply an id. Catalog ids (`CardSet`, `Card`) have no default at all — they are the provider's, which is what makes a re-sync an idempotent upsert.

**`prisma` and `@prisma/client` are pinned to the same exact version** and must move together. Do not run `pnpm up prisma`: the `latest` dist-tag for the CLI currently points at an 8.0 release candidate while the client is on stable 7. `prisma generate` runs as a `postinstall` in `apps/api`, so a fresh `pnpm install` produces a client without a separate step.

## Check constraints

Prisma has no syntax for them, so they are added by hand in their own migration — see `economy_check_constraints` and `trade_check_constraints`.

**This is safe, and it was verified before being relied on.** Prisma's migration engine models tables, columns, indexes and foreign keys. It has no concept of a check constraint, so it neither reports one as drift nor emits a `DROP` for it on a later migration. Tested by adding three by hand, then making an unrelated schema change: `migrate status` reported "up to date" and the new migration contained only the `ADD COLUMN`. Replaying the whole history into an empty database reproduced all of them.

**It does not generalise to indexes.** Prisma _does_ model those, so a hand-written index would be seen as drift and dropped. That is why the "at most one price snapshot per card per day" rule is enforced by the price sync job rather than by a unique index over `capturedAt::date`.

> **The trap.** `prisma migrate dev --create-only` writes `-- This is an empty migration.` **with no trailing newline.** Appending to the file with `>>` glues your first statement onto that comment line, where it is silently skipped. Overwrite the file instead of appending.
>
> It hides well. When this happened during PD-24, the test row was still rejected — by a neighbouring constraint — so the result looked green while one constraint was missing entirely.
